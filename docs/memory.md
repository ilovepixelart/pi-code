# Persistent memory

Per-repository memories with a session-injected index. Source: [`extensions/memory.ts`](../extensions/memory.ts).

- Memories live under `memory/` in pi's agent directory (`~/.pi/agent`, relocated by `PI_CODING_AGENT_DIR`), keyed on the repository root, so subdirectory sessions and every worktree of one repository share a store (as Claude does; this is pi's own store, separate from Claude's).
- The index is injected each session within Claude's 200-line/25KB bound; YAML frontmatter and block HTML comments are stripped before it counts or loads.
- A save landing near the index read limit reminds Claude to shorten it; over the limit the write still succeeds and an error tells Claude to rewrite the index, per Claude's contract. A memory written with frontmatter gets a `modified:` ISO timestamp; the tool asks for Claude's documented `type` vocabulary (user/feedback/project/reference).
- Honors `autoMemoryEnabled` (settings) and `CLAUDE_CODE_DISABLE_AUTO_MEMORY` (env) to turn it off, and `autoMemoryDirectory` (absolute or `~/`) to relocate the store; managed policy settings win over the file chain.
- `autoMemoryStorage: "claude"` (any settings scope) selects the store Claude Code itself keeps — `<claude config>/projects/<project>/memory/`, with the project keyed on the repository root exactly like pi's own, so subdirectory sessions and worktrees share one directory. The store is read and written in place: memories saved from Claude Code appear in pi sessions and vice versa. Claude's underscored file names, arbitrary link titles, ` — ` description separators, and section headings survive a pi edit; an explicit `autoMemoryDirectory` still wins over the storage mode, and nothing is moved or merged when the mode changes.
- `/memory` prints the store, index, and every documented memory-file location (user and project CLAUDE.md, CLAUDE.local.md, the `.claude/CLAUDE.md` alternate), including files that do not exist yet. `/memory edit` picks one of them and opens it in your editor, the one pi's own external editor uses (its `externalEditor` setting, then `VISUAL`, then `EDITOR`), with the terminal handed over; the editor writes the file itself, so its bytes are never normalised. A symlinked file is listed with its real target. It needs the interactive UI.
