# Skills

Bridges `.claude/skills` into pi's skill discovery. Source: [`extensions/skills.ts`](../extensions/skills.ts).

- Skills load in Claude's precedence order: the enterprise directory beside the managed settings file, then personal `~/.claude/skills`, then (approval-gated) every project `.claude/skills` between the working directory and the repository root. `CLAUDE_CODE_DISABLE_POLICY_SKILLS` drops the enterprise directory from the scan; personal and project skills are unaffected.
- pi's loader reads `name`, `description`, and `disable-model-invocation`. Loader-side gaps, documented rather than hidden: other frontmatter fields (including `yes`/`on`/`1` boolean spellings) and the first-paragraph description fallback are pi-loader territory; a description-less skill may be dropped from the listing.
- `context: fork` runs the skill in a subagent via the agent seam: the expanded content becomes the subagent's prompt (no conversation history), `agent:` picks a discovered agent type. As in Claude, the fork runs in the background and its result arrives in the conversation when it completes; it waits in the invoking turn instead when the skill sets `background: false`, in a non-interactive run, when `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, or while an earlier invocation of the same skill is still running. A result that lands after `/new`, `/resume`, `/fork` or `/reload` arrives in the session current at that moment, or at the next session start when none is; in a session that has not had a turn yet it is recorded and reaches the model with the next prompt, as for background subagents.
- `skillOverrides`: a personal or project skill set to `"off"` refuses `/skill:name` with a notice; `"name-only"` listing visibility is pi-loader territory (noted gap). Plugin skills are not affected by `skillOverrides`, as in Claude Code: a key such as `deploy` or `kit:deploy` changes nothing for `/kit:deploy`. Turn a plugin's skills off by disabling the plugin in `enabledPlugins`.
- Invoking `/skill:name` expands the body through the shared command pipeline, as Claude documents that commands and skills "work the same way": `` !`cmd` `` spans, `@file` references, `$ARGUMENTS`/positional substitution, and `${CLAUDE_*}` variables, with the same shell-execution gate commands use.
- A skill whose frontmatter does not parse is not registered. pi's loader skips a personal or project skill with a diagnostic; a plugin skill gets no command and no `plugin_skill` entry, and a warning names the file. Typed input that names such a skill is passed on unexpanded instead of failing.
- Plugin skills register as `/plugin:name` commands rather than through pi's loader. Their descriptions and argument hints appear in the menu, and user invocation uses the same body expansion, hooks, plugin variables, and fork behavior as `/skill:name`. Personal/project skills keep `/skill:name`. The explicit form `/skill:plugin:name` also works. The name is the frontmatter `name` (the directory name without one); when the two differ, `plugin:<directory>`, Claude's internal name for the skill, resolves to the same skill for typed input, `plugin_skill` and subagent preloading, without a second menu or listing entry. A plugin skill marked `user-invocable: false` gets no command, and typing either form is refused with a notice; the model can still run it. Use that form for `pi -p` on older pi versions whose print mode exits before an extension command's submitted prompt starts.
- Deprecated: `/skill:name` without the plugin prefix still runs a plugin skill. It resolves when exactly one enabled plugin ships a skill of that name and no personal, project or pi skill has it, and prints a notice once per process naming the replacement `/plugin:name`. When several plugins ship the name it runs nothing and lists the qualified names. The bare form will be removed in the next major version; use `/plugin:name` (or `/skill:plugin:name`).
- The model calls plugin skills through `plugin_skill`. The tool rechecks invocation restrictions and uses the current call's working directory. Model calls never execute injected shell, and a `context: fork` result returns through the tool instead of posting to the chat. Its listing is rebuilt at every session start and reaches the model through the tool's `prepareLoadout` hook, which pi runs each time it applies the active tools (before a request, and when the active set changes). A pi older than 0.99.0 has no such hook and keeps the description from registration: restart after changing the plugin roster. The `slash_command` tool defines no `prepareLoadout` hook, so its description stays at the list of the session that registered it.
- `allowed-tools: Skill` and `disallowed-tools: Skill` cover both `slash_command` and `plugin_skill`. `Skill(name)` and `Skill(name *)` scopes apply to both tools, including their native pi spellings. Hook matchers receive `Skill` for either tool. Subagent `tools` and `disallowedTools` expand `Skill` to both tools as well.
- Subagent `skills` preloading accepts qualified plugin names such as `kit:deploy`. A bare name resolves in Claude's order: a personal or project skill of that name, then the skill of the plugin the agent itself belongs to, then the first plugin that ships the name. Plugin bodies are resolved from the plugin discovery map without putting plugin directories back into pi's native skill listing.
- Injected-span divergences: a span that exceeds the 2-minute timeout is killed and aborts the invocation (pi has no auto-background Bash set); the exit-1 carveout uses Claude's per-shell sets (bash keeps `find`/`diff`; PowerShell keeps `grep`/`git diff` but not `find`/`diff`). Stacked multi-skill messages (`/a` then `/b` in one message) expand only the first, and `@file` references outside the working directory stay literal (a deliberate hardening).
