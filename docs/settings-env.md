# Settings `env`

Exports `env` blocks from settings into the session. Source: [`extensions/env-settings.ts`](../extensions/env-settings.ts).

- The project is the git repository: a monorepo package is not its own project. Shared state resolves a worktree to its main checkout, so `settings.local.json` and the memory store follow the repository across every worktree of it. `CLAUDE_PROJECT_DIR` instead names the checkout the session runs in, which in a worktree is that worktree ([`internal/project-root.ts`](../extensions/internal/project-root.ts): `repoRoot` for the shared ones, `checkoutRoot` for this one), so a hook script it points at is the copy in the tree being edited. `settings.local.json` sits at that root except outside a repository, when the root is your home directory, on Windows, or when the root or its `.git` or `.claude` entry belongs to another user; in each of those it stays beside `.claude/settings.json` in the working directory, and a legacy file left there is still read with the root's values winning.
- Reads `managed-settings.json` (plus `managed-settings.d/*.json` drop-ins, merged alphabetically after the base file with Claude's rules: single values replace, lists union, nested blocks merge), `~/.claude/settings.json`, the project `.claude/settings.json`/`settings.local.json`, and the `--settings` flag, per-key with Claude's settings precedence: managed > `--settings` > project (with `settings.local.json` overlaying `settings.json`) > user.
- A settings value replaces a value inherited from the shell, as Claude documents, and an empty string is the documented override for an export that cannot be unset; when a later session no longer defines a key, the shell's original value is restored.
- The project scope is approval-gated (a repo's env can redirect providers), and the keys a checked-out repository must not control (`CLAUDE_CONFIG_DIR`, `HOME`, the TMP family, `XDG_*`, content-exporting telemetry variables, start/sync variables, pi's own `PI_CODING_AGENT_DIR`, and the `PI_CODE_*` variables pi-code reads as instructions rather than data) are dropped from project and local settings with a warning; set those in the shell, user settings, or managed settings instead.
- An edit to an `env` block reaches the running session: the settings chain is watched and the merged environment re-applied on save, as Claude applies most settings edits without a restart. Keys the extension owns are tracked, so removing one restores the value it replaced rather than leaving it behind.

## Command-line flags

Claude's two settings flags, with Claude's names and rules ([`extensions/settings-flags.ts`](../extensions/settings-flags.ts), [`internal/cli-settings.ts`](../extensions/internal/cli-settings.ts), spec in [`specs/settings-flags.md`](specs/settings-flags.md)). They apply to every consumer of the settings chain: hooks, `env`, the statusline, output styles, memory, `claudeMdExcludes`, the skill-shell policy, MCP allow/deny and consent lists, plugin enablement, and the user-only keys (`askUserQuestionTimeout`, `preferredNotifChannel`, `cleanupPeriodDays`). pi's own settings are untouched.

- `pi --settings <file-or-json>`: a settings JSON file, or an inline JSON object, applied above the user, project and local files and below managed settings for this session. A value that does not parse as a JSON object is a path, resolved against the working directory. One value per run, as in Claude Code; pi's extension flags are single-valued, so a repeated flag keeps the last. It is the user's own input, so it needs no project approval and its `env` keys are not sanitized.
- The value is read once at startup into a private copy that `/new` and `/reload` reuse: a later edit is not applied, as Claude's reload covers only user, project, local and managed settings. Subagent children are handed the copy, so a concurrent invocation regenerating the original cannot reach a running session.
- A missing file, a path that is not a regular file, a file over 2 MiB, invalid JSON or a non-object is refused with Claude's message (`Settings file not found: ...`, `Cannot use settings file (...): ...`) and the session ends, as Claude exits 1: pi's own shutdown in a terminal session, exit status 1 in print and rpc mode. Extensions loaded earlier have already begun their session start by then, so a refused flag fails closed and no settings file loads in that window.
- `pi --setting-sources user,project,local`: only the named file sources load. An empty list loads none; managed settings and `--settings` always apply. An unknown name is refused (`Invalid setting source: ...`) and the session ends. Project and local files remain approval-gated. Leaving `user` out also drops its `enabledPlugins`, so an installed plugin with no entry left runs by its manifest's `defaultEnabled`.
- Limit: the MCP allow/deny policy computed while pi loads its extensions, before pi has parsed any flag, does not see `--settings`; the per-session policy does.
